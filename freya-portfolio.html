01 / SYSTEM OVERVIEW

拍题答疑产品与系统全景

用户拍一道题进来，系统不是直接把图丢给大模型，而是先过「识别 → 路由 → 解题 → 质检」四道关，再把解题过程返回；错题自动沉淀进错题本，按学科分类、按遗忘曲线复习。

用户输入 · Input
拍照上传
单题 / 整页试卷多题批量识别
题干完整度预检
模糊 / 倾斜 / 残缺 → 提示重拍，不硬答
设计细节

缺条件时提示重拍或补全。需要同时观察拦截准确性与误拒答，避免通过少答难题虚高准确率。

7 维分类路由
是否为题 · 题干完整度 · K12/非K12 · 题目数量 · 答案唯一性 · 图表 · 题型
设计细节

这些是输入路由维度，和评测用的学科 / 学段 / 题型标签分别管理。评测路由准确性，再评测各路径的解答表现。

双路径解题
常见题 → LLM 直解（速度）
长尾难题 → RAG 题库检索（准确率）
设计细节

检索并不保证答案正确。召回后核对原题与条件，匹配不足时重新求解或兜底，并记录时延与错误类型。

设计细节

质检是一项职责，不能当成 Badcase 第四层。归因需要追到识别、理解、生成或最终答案；质检漏检可作为附加标签。

北极星

周有效解题数

获得解答或批改、且查看了解题过程的用户行为次数。比「拍题次数」更能代表产品真实价值——反映解答被查看与使用；是否学会仍需测验或后续行为验证。

核心漏斗

拍题 → 识别 → 解答 → 查看 → 讲解

每 2-3 周跑一次分层分析（学段 × 学科 × 题型），定位瓶颈环节。结合识别成功率、解答覆盖和查看率定位瓶颈，避免只盯总准确率。

互证原则

离线质量评测与线上反馈互证

离线提升后，继续观察线上投诉、应答率和时延。变化不一致时，排查题目分布、采样与体验因素，再判断是否存在评测盲区。

02 / AGENT ARCHITECTURE

多 Agent 协作 + 分类路由 + 工具调用

把一个「拍照→解题」的模糊需求，拆成识别、理解、推理、质检四个分工明确的 Agent；再用 7 维分类路由决定走哪条解题路径，用置信度判断决定什么时候触发检索、什么时候降级兜底。

Agent 职责与协作机制

Agent 01

题目识别

OCR + 题目检测，处理模糊、倾斜、整页多题；识别不完整直接提示重拍，不进入下游。

Agent 02

题目理解

拆解题意、学科分类、难度判定；输出结构化题干给下游，并决定路由方向。

Agent 03

解题推理

按学科解题 Skill 输出分步过程；常见题直解，长尾题先 Embedding 召回题库原题和标准答案。

Agent 04

答案质检

安全合规、答案正确性、步骤完整性、讲解体验四层校验；不通过自动重生成或降级。

双路径解题策略与适用边界

路径 A · 速度优先

常见题 → LLM 直解

基础题、高频题、答案明确的题，直接让大模型生成解题过程。延迟低、体验流畅，覆盖大部分日常使用场景。

路径 B · 准确率优先

长尾难题 → RAG 题库检索

对长尾难题尝试题库召回，核对题干、条件和解析的匹配程度；检索质量与解题正确性分别评测，避免相似题误用。

题库检索增强 · 离线构建与在线查询

长尾难题和以图为核心的题，先查题库里的原题和标准答案，再决定直接采用、作为参考，还是交给模型直解。检索与模型侧由算法团队落地，我负责方案、阈值策略和评测口径。

🧱 离线构建

  1. STEP 01
    入库单元

    一道题一条记录，不切块（题目本身就是最小语义单元，切开会丢条件）。

  2. STEP 02
    字段

    规范化题干（OCR 文本，公式统一成 LaTeX）、学科、题型、知识点、标准答案与解析、来源。

  3. STEP 03
    向量化

    对题干 + 关键条件做 embedding；学科、题型作为元数据，用于过滤。

  4. STEP 04
    更新

    线上错题与 Badcase 经核验后回流，补进题库和评测集。

🔍 在线查询

  1. STEP 01
    构造 query

    识别文本 + 题面特征（学科、题型、关键条件）。

  2. STEP 02
    召回

    按学科 / 题型过滤后，召回候选原题。

  3. STEP 03
    相似度校验

    候选与题干逐项比对，置信度高于阈值才作为标准答案输出（用阈值校验代替重排，重点防「相似题误用」）。

  4. STEP 04
    降级

    命中但置信度不够 → 不直接采用，作为参考输入交给模型直解；检索失败 → 回退模型直解。

检索设计取舍

设计点选择为什么
切块一题一条，不切条件被切开，最容易出现「看起来像、其实不是」的假命中
触发按路由结果条件触发，不是每题都查控制时延和成本
采用阈值以上才当标准答案，以下只当参考防假命中直接给到用户
评测检索质量和解题正确性分开评避免检索命中率掩盖答案错误

工具调用与降级兜底

机制怎么做解决什么问题
检索条件触发不是所有题都检索，按难度路由结果决定控制延迟和成本，避免每道题都查库
置信度判断结合输出一致性、检索匹配与质检信号触发兜底；模型自报置信度需校准避免「一本正经地胡说」直接给用户
失败自动降级检索失败 → 回退 LLM 直解；直解失败 → 提示用户换问法保持服务可用；仍需对最终答案做质量校验
长期记忆 · 错题本自动收录错题、按学科沉淀；结合用户历史做个性化讲解从「一次性答疑」变成「学习闭环」

03 / KEY DECISIONS

关键产品决策与取舍

从产品目标出发，说明为什么选择这条路径，以及如何检查它有没有解决问题。展开查看决策边界与取舍。

D01

分阶段处理与质量控制

识别、理解和求解的错误会叠加。先检查题干完整性，再按题目特征选择路径，减少下游在错误条件上继续推理。

决策边界与取舍

先确定模型能力边界，再做产品承诺。质量验证与时延预算需要一起考虑。

D02

七维分类与解题策略路由

同一路径难以兼顾简单题的速度与复杂题的可靠性。用输入特征组织策略，对直解、检索和兜底分别做分层评测。

决策边界与取舍

路由本身也会犯错。要核对输入分类准确性，不能只验下游模型。

D03

有效解题指标与价值衡量

拍题量只说明用户发起请求。获得解答并查看过程，更接近产品被实际使用；同时观察应答覆盖、错误反馈和时延。

决策边界与取舍

查看不等于学会。学习效果需要测验、复习表现或后续行为证据。

D04

正确性判定与过程质量评价

正确性回答「答案是否成立」，Rubric 回答「步骤是否完整、讲解是否好用」。两套口径分别统计，不能用体验高分掩盖错误答案。

决策边界与取舍

主观题按关键要点与允许解法判定正确 / 错误 / 待仲裁；待仲裁样本暂不进入正确率分母，并单报占比。

D05

试标校准与评测规模扩展

先用小规模典型题检验规则是否可执行，校准标注分歧，再扩充学科与题型覆盖。后期单轮约 1,000–2,000 题，各轮题目不同。

决策边界与取舍

固定错题回归与阶段分层评测服务不同目的。跨批次比较需要说明组成差异，不只给一个总分。

D06

错误样本回流与定向回归

把线上问题按识别、理解、生成、最终答案分层，形成优化优先级，再用同类题做定向回归，检查是否修复及是否引入新退化。

决策边界与取舍

处理线上样本前先考虑授权和脱敏；回流数量本身不是效果，应观察重复错误与回归表现。

04 / EVALUATION SYSTEM

解题质量标准与评测体系

这是我在这个项目里做得最深入的一块。面对跨学科答案标准不一、全学科专家不够用、模型效果难客观判断的痛点，我搭建质量标准、标注规则、错误归因和版本对比流程。

两套口径，分别使用

解题正确率 = 判定正确的样本 ÷（正确 + 错误的样本）。可解题误拒记为错误；缺条件、矛盾或不可解且被正确拒绝的题与待仲裁样本单列。开放作文与批改单独评价，应答率另计。0–4 分质量档位用于过程与体验评价，不能替代解题正确率。下表是作品集中的概括说明。

五层质量标准

L1

安全层

内容安全、合规、敏感信息拦截。教育场景红线。

L2

意图层

有没有答非所问？是不是真的在解这道题，而不是自说自话。

L3

正确性层

客观题核验答案；主观题按关键要点与允许解法判定正确、错误或待仲裁。

L4

完整性层

解题步骤全不全？是不是只给了个答案跳步了？

L5

体验层

讲解是否清晰易懂、格式是否规范、有没有引导到下一步。这一层影响阅读体验；复用意愿需用线上行为验证。

0–4 分质量档位与判定依据

档位等级判定标准
4 分好用主需全满足 + 延展全满足 + 未命中陷阱
3 分可用主需全满足 + 未命中陷阱（延展未满足或轻微错误）
2 分部分可用核心需求部分缺失，仍有可用内容；无严重错误
1 分没用核心需求严重缺失，或存在严重错误
0 分完全没用主需全部缺失或全部错误

跨学科参考答案核验与争议处理

方法 01

原题与标准解析核验

从题库、练习册、往年真题里找原题和标准答案，作为参考答案基线。

方法 02

多模型答案一致性参考

用多个不同厂商的模型分别作答，一致性用作辅助线索，不能替代原题解析与人工仲裁；模型也可能共同犯错。

方法 03

竞品对比

和作业帮、小猿等成熟产品的解答对比，不一致的题重点人工复核。

核心思路：评测体系不是一开始就完美的，是在迭代中不断完善的。先搭一个能跑起来的框架，先小规模试标，统一规则，再扩展到不同批次的评测题。版本对比同时检查分层表现与应答覆盖；保留典型错题作定向回归。

05 / ATTRIBUTION FLYWHEEL

四层错误归因与迭代闭环

模型解题不准，但问题根因不清——是识别错了？理解错了？还是生成错了？建立四层归因框架后，每 2-3 周输出一次效果报告，明确短板和优化优先级。

L1 图像识别错
模糊 / 倾斜 / OCR 错
→ 优化前置处理 + 重拍提示
L2 题目理解错
分类错 / 意图路由错
→ 优化分类规则与 Prompt
L3 解题生成错
推理链错误 / 运算错误 / 逻辑跳步
→ Prompt + RAG 策略优化
L4 最终答案错
过程正确但结论 / 选项 / 单位错
→ 检查过程与最终输出的一致性
↓ 按根因归档，回流分层评测与定向回归 ↓
数据飞轮：评测 → 归因 → 优化 → 回归 → 线上错题回流评测集
每 2–3 周输出阶段效果报告，定位短板与优化优先级

错误诊断与优化策略

检索策略

检索触发与匹配质量

按题目特征触发召回，核对原题与条件，重点评测相似题误召回；同时观察增加的时延。

输入质量

输入质量预检与补充引导

对模糊、倾斜、缺失条件提供重拍或补充信息入口；分开评测识别质量与下游解答。

标注校准

标注分歧校准与规则完善

关键要点、允许解法与错误类型明确后再扩充样本。争议题保留待仲裁，不强行计入正确率。

错误归因案例：识别偏差与答案不一致

合成演示 · 非线上样本假设输出 / 未运行模型测试
题面 / 合成文字输入

长方形的面积

长方形长 2 m，宽 30 cm。
面积是多少平方米？

2 m30 cm

参考解：30 cm = 0.3 m
2 × 0.3 = 0.6 m²

假设错误输出

宽 30 cm = 0.3 m，面积为 2 × 0.3 = 0.6 m²。
因此，最终答案是 60 m²。

正确性判定错误L4 · 最终答案
判分依据

中间计算成立，最终结论与计算结果不一致；不能因步骤正确就判整题正确。

迭代动作

增加最终结论与推导结果、单位的一致性检查，保留同类错题作定向回归。

复核条件（待实际测试）

同类单位换算题最终答案与过程一致；同时检查应答率和时延是否退化。

案例分析：判定、归因与验证

根据题干、解题过程与最终答案定位错误，明确判分依据，再提出改进动作与回归验证条件。本例为合成演示，用于展示分析方法；不代表公司真实样本或已验证的改进效果。

演进时间线

  1. v1.0 方案定稿

    产品边界定义（什么算题、题干不完整到何种程度不可解）；分类路由 + 「模型直解 + 题库检索」双路径；五层评测标准建立。

  2. 评测闭环运转

    四层 Badcase 归因，每 2–3 周输出效果报告、定迭代优先级；线上错题回流评测集。

  3. v2.0

    分类升级为 7 维；多 Agent 架构与工具调用正式化；「快速解答 → AI 精讲」分层讲解，错题本与长期记忆。

  4. 结果

    解题准确率由 72% 提升至 90%。

06.2核心产品决策

D01

48 小时内为什么用 API 组合，不自研模型？

五个环节逐一比较开源方案和第三方 API 的开发周期与可行性，选最快跑通核心链路的组合。POC 要回答的是「值不值得做」，不是「能不能自研」。

取舍

代价是按量计费和供应商依赖；需求验证成立后再评估自建或私有化。

D02

为什么把五个技术环节封装成三步？

内容团队要的是出片，不是调参数。抓取、写稿、配音、驱动、合成都放到后台，前台只留「粘贴链接 → 选形象 → 出片」。

取舍

高级参数（音色、语速、风格）收进二级面板，默认值保证第一次就能出片。

D03

1.0 为什么不建知识库，而是实时抓取单篇？

口播的素材就是用户给的那一篇文章，实时抓取保证内容最新、来源唯一可追溯；建库的收益要等到多篇聚合时才出现。

取舍

稿件逐条标来源，只有一个来源时提示「单一来源」，提醒编辑核实。

D04

口型驱动为什么设计主备两家？

口型驱动是链路里最贵、最不稳定的一环，单一供应商出问题整条链路就停。主用效果优先的方案，备用保证可用。

取舍

主备切换对用户透明；评测按同一套口型同步和画面质量标准比较两家。

D05

2.0 为什么拆成五个 Agent，并且每步都要确认？

短片创作是长链路，一步错步步错。拆成剧本、角色、分镜、参考图、视频五个分工明确的 Agent，每个阶段输入输出固定，用户确认后再往下走，不满意只重生成这一环。

取舍

比一键全自动慢，但返工成本最低；后续对稳定的环节开放「自动连续执行」。

D06

角色一致性为什么用 ID 锚点，不用相似度检索？

同一个角色在不同镜头里「认错人」是短片最致命的问题。分镜里直接引用角色、场景 ID，精确取回设定图做参考，结果可预期。

取舍

相似度检索留给跨项目找素材，不用在同一项目内锁定角色。

06.5数据 / 检索双链路

当前方案（已落地的设计）

1.0 在线链路：文章链接 → 抓取并清洗正文（去导航、广告、脚注）→ 单篇正文上限 6,000 字，整篇进上下文 → 口播稿逐条标注来源 → 来源只有一个时提示「单一来源」。

2.0 资产链路：剧本 JSON → 角色设定卡（结构化字段 + 4 视图）和场景全景图 → 分镜脚本按场次拆镜头，引用角色 / 场景 ID → 参考图生成时按 ID 精确取回设定图做锚点。

规模化方案：多篇聚合 / 跨项目资产复用时上向量库

🧱 离线构建（INDEXING）

  1. STEP 01
    解析

    网页正文抽取；资产库读取结构化设定卡。

  2. STEP 02
    差异化切块

    文章按自然段落，300–500 字，重叠 10–20%；角色卡、场景卡、分镜一条一条存，不切。

  3. STEP 03
    向量化

    文本用中文 embedding（如 bge-m3 / 百炼 text-embedding）；设定图用图像向量（CLIP 类）。

  4. STEP 04
    入库

    pgvector 或 Milvus，HNSW 索引；元数据记来源 URL、发布时间、作者、角色名、风格标签、项目 ID。

🔍 在线查询（QUERY）

  1. STEP 01
    Query 构造

    口播主题 / 分镜描述 + 角色名 + 风格。

  2. STEP 02
    混合检索

    向量 Top-20 + 关键词 Top-20，RRF 合并，按项目、风格、时间做元数据过滤。

  3. STEP 03
    重排

    取 Top-5，相关度低于阈值不进上下文。

  4. STEP 04
    生成

    强制标注来源；资产类结果由用户选定后再作为锚点。

06.6质量治理手段

来源引用

口播稿每条事实带来源链接，单一来源给出提示。

禁编规则

不编造数字、日期、机构，规则扫描兜底。

收尾评估器

成稿前过一遍事实和口播可读性检查，不过关就带着问题重写。

角色一致性锚点

角色设定贯穿剧本、分镜、参考图。

参考图质检

视觉模型按角色匹配度、构图、画面瑕疵打分，≥7/10 放行，最多重做 3 版，仍不过就交给人工。

阶段停点

每个阶段用户确认后再往下走，不满意只重生成这一环。

06.7评测体系

1.0 口播稿

1.0 成片

口型同步、音画一致、画面瑕疵、完整出片。

2.0 剧本

镜头连贯、角色一致、动作自然。

D01

多 Agent 为什么由主控引擎统一编排？

PM 判断

剧情前后一致比每个角色自由发挥更重要。扩写首幕、下一幕、结局、配图四个角色分工明确，分支、记忆和存档由引擎统一管理，避免各说各话。

D02

为什么用结构化记忆，不做全文摘要压缩？

PM 判断

摘要会丢伏笔。每幕把已确认事实、关键选择、未解悬念、待回收和已回收伏笔写进记忆，窗口只带最近 3 幕原文，连贯性和成本兼顾。

D03

为什么同时给选项和自由输入？

PM 判断

选项降低门槛，自由输入保留脑洞；自由输入先过内容安全检查，再由引擎并入剧情。

D04

怎么让剧情不落俗套？

PM 判断

每个题材 Skill 带发散算子和套路黑名单，生成后做套路检测，命中就带着指令重写。

D05

内容安全为什么只拦危险指导？

PM 判断

叙事游戏需要冲突和反派，一刀切会让故事变平；安全线放在现实危害上，题材上保留张力。

D06

为什么给每局设模型调用上限？

PM 判断

防异常循环、控制成本，让一局在可控的调用次数内完成。

08.2核心产品决策

D01

为什么用固定流水线，不做自由编排？

PM 判断

产品文档的阶段有天然依赖：没澄清就写不了摘要，没证据就不该写定位。固定流水线让每一步都能停下来审核。

D02

为什么用证据卡，不直接上向量知识库？

PM 判断

竞品最多 3 个，证据几十条以内，按编号整体注入比相似度召回更可控，而且每条结论都能精确指回某一张卡。

D03

为什么竞品由用户自选，不内置种子竞品？

PM 判断

内置竞品和用户的想法常常不相关，还会把没有出处的描述带进 PRD。把选择权交给用户，模型推荐的竞品一律标「合理推断」。

D04

为什么做引用审计，不只靠 Prompt 约束？

PM 判断

Prompt 只能要求，审计才能保证。编号不存在就剔除；结论型章节没有证据就进「无证据结论清单」。

D05

上游改了怎么办？

PM 判断

上游阶段被修改时，下游产物自动失效、提示重生成，避免旧结论覆盖新决定。

D06

质量和速度冲突时先保哪个？

PM 判断

先保质量：8 维澄清问题要贴合具体想法，生成慢一点可以接受；体验上改为异步任务和进度提示。

08.5数据 / 检索链路

当前方案

用户自选竞品 → 校验公网地址后抓取 → 清洗导航、脚本、页脚 → 模型抽成结构化证据卡（来源链接必填）→ 存库 → 生成定位和 PRD 时按编号注入 → 引用审计。

规模化方案（跨项目沉淀竞品知识库）

🧱 离线

  1. 一张证据卡一条记录，embedding 文本为「结论 + 启发 + 原文摘录」，元数据记竞品名、证据类型、置信度、来源、抓取时间；原始网页另存，用于追溯。

🔍 在线

  1. 需求摘要 + 当前章节作 query → 向量 Top-20 → 优先「已确认」证据 → 重排取 5–8 张注入 → 仍要求引用编号，审计照旧。

评测

章节应引用证据的召回率、引用有效率、无证据结论占比。

08.6质量治理与评测

治理

引用编号存在性校验；只保留真实引用；结论章节无证据进清单；置信度分级，用户确认后才升级为「已确认」；预算护栏防异常循环。

评测

固定一组产品想法作为回归集，每次改 Prompt 都重跑；产品经理按 5 个维度给样例打分，判定可接受 / 不可接受。

指标口径

澄清完成率、竞品证据添加率、PRD 生成完成率、资料包导出率、研发任务采纳率、引用有效率。

09 / AI PM METHODOLOGY

AI 产品设计与质量管理方法

结合拍题答疑与个人项目实践，从数据、工作流、任务边界和评测四个角度组织产品设计与质量管理。

AI 产品的长期价值来源

L1
数据飞轮

把经授权、可复核的问题反馈转为评测样本，检查优化后重复错误是否减少。使用量增加不等于数据质量自动提高。

L2
工作流嵌入

先理解用户在什么任务节点需要帮助，再衔接输入、结果与后续动作。能否形成习惯，需要留存与重复使用证据。

L3
垂直领域知识壁垒

领域标准、错误分类与高质量参考答案需要持续校准。产品、算法和标注共同维护规则，让质量判断可解释、可复核。

L4
社区与网络效应

当用户之间的内容与协作带来额外价值时，才可能形成网络效应；不能仅凭用户规模推断护城河。

Agent 任务边界与可靠性

短期

任务边界与自主性控制

多步链路会增加失败入口，不能只验单个 Agent。先界定可可靠处理的任务，再评测端到端成功率、失败恢复、时延与成本。

长期

场景理解与持续质量评测

模型与工具会持续变化。产品需要积累场景理解、质量标准和用户信任，并用评测验证换模型或改工作流之后是否仍然可靠。
